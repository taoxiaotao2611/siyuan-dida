# Dida CLI 0.1.14 Snapshot Protocol Design

## Goal

Accept the current latest Dida CLI release (0.1.14) for task snapshots without weakening the fail-closed version gate that protects unbound SiYuan todos from duplicate Dida task creation.

## Background

Every snapshot request is gated on a per-version protocol record describing how many rows the CLI's `task filter` and `task completed` commands may return and which completed-task date bounds the backend honours. A version without a record is rejected before the request is made, which blocks recovery and new unbound task creation instead of risking duplicates.

Before this change only CLI `0.1.10` had a record. Users of the latest release saw this on every sync:

```text
Incomplete snapshot unsupported for dida CLI version 0.1.14; verified version: 0.1.10
Completed snapshot unsupported for dida CLI version 0.1.14; verified version: 0.1.10
```

## Verification of 0.1.14

Verified on 2026-10-22 against `@suibiji/dida-cli@0.1.14` (the npm `latest` dist-tag), installed and authorized locally. All probes were read-only API calls:

| Probe | Result |
| --- | --- |
| `dida --version` | `0.1.14` |
| `dida task filter --status 0 --json` | 39 rows; every row has `id` and `projectId` |
| `dida task completed --start-date 1970-01-01T00:00:00Z --end-date 9999-12-31T23:59:59Z --json` | exactly 200 rows, i.e. the server still caps this endpoint at 200 |
| completed window `2026-10-21T00:00:00Z`..`2026-10-22T00:00:00Z` | 2 rows |
| completed window `2026-10-01T00:00:00Z`..`2026-10-23T00:00:00Z` | 57 rows |
| completed window `1990-01-01`..`2000-01-01` and `2030`..`2031` | 0 rows, so both bounds are honoured rather than ignored |
| single-project filter | only that project's rows returned |
| `completedTime` shape | `yyyy-MM-ddTHH:mm:ss.SSS+0000`, parsed by `Date.parse`, never `NaN` |

The installed CLI's compiled source confirms the reason the protocol is unchanged: `task filter` and `task completed` post the same `projectIds`/`startDate`/`endDate` body to `/open/v1/task/filter` and `/open/v1/task/completed`, do not truncate or paginate results client-side, and print `JSON.stringify(data, null, 2)` in `--json` mode.

## Change

- Add `0.1.14` to the snapshot protocol map with the verified `resultLimit` of 200 and the completed-task upper bound `9999-12-31T23:59:59Z`.
- Keep `0.1.10` supported.
- Continue rejecting every other version before any snapshot request.
- Build the rejection message from the protocol map so the list of verified versions cannot drift from the code.

## Safety

The safety behavior is unchanged: an incomplete snapshot at the 200-row limit blocks creation; completed snapshots are sharded by date with a query budget and wall-clock deadline; every row is checked for `id`, `projectId`, and a `completedTime` inside the requested interval. Only the explicit version allow-list grows.

## Testing

- `0.1.14` is accepted for both snapshots with the unchanged argument mapping.
- `0.1.14` enforces the 200-row incomplete-snapshot limit.
- `0.1.14` completed snapshots still shard a saturated interval instead of trusting 200 rows.
- `0.1.11`, `0.1.13`, and `0.1.15` remain rejected, and the error lists both verified versions.
- Full unit suite, TypeScript type check, production build, and local SiYuan installation.
